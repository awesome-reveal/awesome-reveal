# Astro adapter

- `Reveal.astro` and `Cascade.astro` render the shared `Host.astro`, and only `cascade` differs. The host sets a `cascade` attribute on `<awesome-reveal>`, which picks `createCascade`. The three files ship uncompiled. Astro compiles the `.astro` files of a dependency that has the `astro` peer dependency or the `astro-component` keyword. `vite.config.ts` copies the files into `dist`, and keeps the `.astro` imports of `index.ts` external. Node cannot import `dist/index.js`, so the package tests load the root entry only through an Astro build.
- `index.ts` exports `Reveal` and `Cascade` with an explicit type, because only the Astro language tools resolve a `.astro` import. A `.d.ts` that imports `Reveal.astro` fails attw, and plain `tsc` cannot resolve it.
- Keep the style of `Host.astro` global, with selectors that start with `awesome-reveal`. With a scoped style, the `where` and `class` values of `scopedStyleStrategy` make the compiler add a `class` after the attribute spread, and the `class` prop is lost.
- The client side is the `<awesome-reveal>` custom element in `src/element.ts`. Astro hydrates nothing, so there is no hydration test.
- `connectedCallback` parses the attributes in a `try`, creates the reveal or the cascade with them, attaches the element, and then throws a parse error again. The options must apply at the attach, because the attach reveals an element that already contains focus, and `when: false` must win over that focus. With invalid JSON, the store gets only `onReveal`, so the viewport still reveals the element, and the browser sends the error to the window `error` event, as it does for each error in a custom element callback. Do not throw before the attach: the element would stay hidden. A host with no element child throws, because the HTML parser moved the rendered tag out of it, for example in a `<p>`. The server render does not validate `as`: a throw there fails the whole page. `when` is its own host attribute, so that `getReveal` can set it with no JSON. Without `IntersectionObserver`, the reveal plays at once. An invalid change after the connection keeps the previous options.
- The host element is internal. User code gets `getReveal(element)` from `src/control.ts`, which reads and writes the attributes of the host and its `revealed` getter. The setter writes the attribute: before the upgrade, the host is a plain `HTMLElement`, so only an attribute reaches `connectedCallback`. `getReveal` accepts only the first element child of a host, which is the element that `connectedCallback` attaches.
- `getReveal` is in the root entry, with no subpath. Astro 6 and 7 replace each `.astro` import in client code with a stub, so a client script that imports the root entry bundles no component. The stub is `{}` in a build, and a function that throws in `astro dev`, so client code must not use `Reveal` or `Cascade`. `control.ts` must not import `element.ts`: the server imports the root entry, and `class extends HTMLElement` throws there.
- `connectedMoveCallback` and the microtask in `disconnectedCallback` keep the state of a `transition:persist` element. The ClientRouter uses `moveBefore()` where it exists, and a remove and append in one task elsewhere. The e2e persist test fails in all three engines without them.
- `Host.astro` moves the `transition:persist` attributes from the inner element to `<awesome-reveal>`. The new body connects before the ClientRouter moves the persisted element in, so a persisted inner element would lose its reveal store.
- The server markup hides the element with `data-awesome-reveal="hidden"`, or the direct children of a cascade with `data-awesome-reveal="cascade"`. The frontmatter of `Host.astro` imports the package `reveal.css`, which the build copies into `dist`. Astro bundles the CSS of the component, so the package has no CSS export and keeps `"sideEffects": false`. `test/build.test.ts` checks that the build keeps the CSS. Do not add a `style` attribute: `security.csp` blocks style attributes. The build test checks the markup with `security.csp`. Astro does not support `security.csp` with the ClientRouter, so the e2e test sets `style-src-attr 'none'` itself and fails on each violation.
- `astro:ssr` lives in `packages/astro/vitest.config.ts`, so that the Astro compiler comes from this package, and the Astro 6 CI job can install Astro 6 only here. A project file does not inherit the root options, so it sets `globals: true`. `test/tsconfig.json` does not include this file: with Astro 6, the Vite types of `getViteConfig` have no `test` key.
- The Vite config of Astro aliases the bare `astro` import to its types. In that environment, import the Astro API, such as `build`, by its resolved path, as `test/build-site.ts` does.
- The programmatic `build` and `preview` need `root` and `outDir` as filesystem paths. With file URL strings, Astro builds 0 pages. The preview server of `@astrojs/node` reports the configured port, so port 0 does not work.
- Astro 6 and 7 give different output: Astro 6 adds `data-astro-source-file` and whitespace in the container, and the minifiers write `@media(` or `@media (` and other quotes. Keep the test patterns tolerant.
- The example and `astro:e2e` need Astro 7, because `@astrojs/node` 11.1.3 and later need Astro 7.2.1 or later. The Astro 6 CI job runs `astro:unit`, `astro:ssr` and `astro:browser`.
- `tsc` cannot read `.astro` files. `test/astro.d.ts` declares them for the tests. `astro check` reports only the files of the tsconfig `include`, so the example tsconfig includes `packages/astro/src/**/*.astro`. The `tsconfig.base.json` paths resolve the imports to the sources. The e2e test also builds the example on the sources.
